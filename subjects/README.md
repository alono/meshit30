# הוספת נושא

הוספה של אחד משלושת המבחנים הנותרים — ימאות ג', ניווט ב' (מכשירים), ניווט חופי — היא הוספת
תוכן בלבד. אין שינוי בקוד האפליקציה.

## 1. יצירת התיקייה

```
subjects/<slug>/
  questions.json     # מאגר השאלות הרשמי — נכתב ביד, לא נוצר אוטומטית, ולעולם לא משתנה
  cheatsheet.md      # דף ריכוז, מוצג בלשונית "חומר עזר"
```

## 2. רישום בקובץ המניפסט

יש לשנות את הערך של הנושא ב-`manifest.json` מ-`"status": "coming-soon"` ל-`"active"`.

## 3. בניית הקבצים הנגזרים

```sh
node scripts/build-terms.mjs   <slug>   # cheatsheet.md  -> terms.json
node scripts/build-display.mjs <slug>   # questions.json -> display.json + repairs.report.txt
node scripts/validate-subject.mjs <slug>
```

או `npm run content` כדי להריץ את שלושתם על כל הנושאים הפעילים.

הכול עובד בלי רשת ובלי מפתחות: אין שלב תרגום. האפליקציה כולה בעברית.

## חוזה הקבצים

### `questions.json`

```jsonc
{
  "source": "…",                  // מקור המאגר, מוצג בתחתית מסך הנושא
  "exam": {
    "questions": 50,              // כמה שאלות נשלפות בכל סימולציה
    "points_per_question": 2,
    "pass": 84,                   // ציון עובר מתוך 100
    "minutes": 60                 // אורך הספירה לאחור
  },
  "count": 178,                   // חייב להיות זהה לאורך questions
  "questions": [
    {
      "id": 1,                    // מספר ייחודי
      "topic": "מבנה המנוע…",     // טקסט חופשי; רשימת הנושאים נגזרת, לא מקודדת
      "question": "…",
      "options": { "א": "…", "ב": "…", "ג": "…", "ד": "…" },  // בדיוק ארבעת המפתחות
      "correct": "ד",             // אחד מארבעת המפתחות
      "note": "…",                // רשות; מוצג בתרגול בלבד (פגמים במסמך המקור)
      "image": "charts/03.png"    // רשות; נתיב יחסי לתיקיית הנושא
    }
  ]
}
```

פרמטרי המבחן שונים בין הנושאים ותמיד נקראים מבלוק `exam`. שום דבר מ-50 השאלות, 60 הדקות או
ציון עובר 84 אינו מקודד באפליקציה.

השדה `image` נועד לניווט חופי, שבו שאלות עבודת מפה יצטרכו שרטוט. הוא נתמך כבר עכשיו, כך
שהוספת השאלות האלה בהמשך אינה שינוי סכימה.

### `cheatsheet.md`

כותרות סעיפים בתבנית `## <מספר>. <עברית> | <English>`. כל טבלת markdown שכותרת העמודה
**השנייה** בה היא `English`, `Symptom` או `Fact` נקראת כטבלת מונחים: עמודה 1 עברית, עמודה 2
אנגלית, עמודה 3 הסבר קצר. שאר הקובץ הוא פרוזה — מוצג, אך לא מפורסר.

הצ'יט שיט הוא הקובץ היחיד שנשאר דו-לשוני. הוא מוצג כמות שהוא בלשונית "חומר עזר"; בכל שאר
האפליקציה אין אנגלית.

### `term-overrides.json` (רשות)

כוונון ידני מעל מה שנגזר מהצ'יט שיט:

```jsonc
{
  "patch": {
    "gearbox-transmission": { "aliases": ["תשלובת"] },      // צורות שהמאגר משתמש בהן
    "propeller":            { "definition": "…" }            // הגדרה עברית לכרטיסייה
  },
  "add":  [{ "id": "…", "he": "…", "en": "…", "definition": "…", "aliases": ["…"], "topic": {…} }],
  "drop": ["some-term-id"]
}
```

כל מונח חייב `definition` בעברית, כי כרטיסיות השינון רצות בשני הכיוונים. ההגדרה אינה יכולה
להכיל את המונח עצמו — אחרת הכרטיס בכיוון ההפוך מסגיר את התשובה. הבנייה נכשלת אם:

* מפתח ב-`patch`/`drop` אינו מתאים לאף מונח שנגזר (סימן לשגיאת כתיב או ל-slug שהשתנה),
* מונח ב-`add` משויך לנושא שאינו אחד מסעיפי הצ'יט שיט (יוצר צ'יפ סינון כפול).

### `text-overrides.json` (רשות)

תיקון הפגמים שקובץ ה-PDF הרשמי הכניס לטקסט:

```jsonc
{
  // מילים אמיתיות שהמאגר מציג רק בצורה שבורה, ולכן אוצר המילים לא לומד אותן לבד.
  // הוספה כאן מאפשרת למנוע התיקון הרגיל לאחות אותן — בלי לכתוב טקסט ביד.
  "vocabulary": ["הבערה", "מפל"],

  // מקומות שבהם ה-PDF שיבש או מחק אותיות, ולכן חייבים לכתוב את הנוסח ביד.
  "questions": {
    "13": {
      "options": { "א": "שמירת אינרציה ויציבות סל\"ד." },
      "reconstructed": ["א"],       // חובה — מסמן שהנוסח אינו רשמי
      "note": "…"                    // מוצג בתרגול בלבד
    },
    "138": { "issue": "…" }          // שאלה שאי אפשר לענות עליה; לא נכללת בסימולציה
  }
}
```

**הכלל שמגן על הטקסט:** התיקון האוטומטי מוסיף, מסיר או מזיז רק רווחים ומירכאות — לעולם לא
אות עברית. `build-display.mjs` מוודא זאת מכנית וקורס אם הכלל מופר, כך שהמינוח נשאר בדיוק זה
של הבחינה. רק שדות המסומנים `reconstructed` פטורים מהבדיקה.

### נגזרים — אין לערוך ידנית

`terms.json`, `display.json` ו-`repairs.report.txt` נוצרים מחדש בכל בנייה.
`repairs.report.txt` מפרט כל שינוי טקסט שבוצע, כדי שאפשר יהיה לעבור עליו פעם אחת ולאשר.
